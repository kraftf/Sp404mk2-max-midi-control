### Cross-group bus-switch label scramble (user-found in first C33 Max test) — FIXED
Symptom: switching BUS1/2 → BUS3/4 or INPUT (any cross-GROUP switch) showed wrong
knob labels until the effect was manually re-selected; 1↔2 and 3↔4 were fine.
LATENT SINCE CONTROL-32 (nothing in C33's other two changes touches bus switching) —
the Control-32 no-hardware test pass evidently only exercised same-group switches.
Root cause: Max fires multiple cords from one outlet right-to-left by destination x,
ties bottom-to-top. From obj-12's outlet: obj-19 (x=260, menu item rebuild) first,
then obj-pv2-busadd (x=40, y=3400 — bottom-most of the x=40 ties) fired BEFORE the
five gate-control selects obj-506/544/582/620/c3132 (x=40, y=362..882). The pv2
refresh therefore injected the new bus's stored menu position into the 5 EFX gates
while the OLD bus's gate was still open, so it was translated through the OLD group's
position→effect mapping (busid_BUS12/BUS34/INPUT differ per group — same-group
switches share a mapping, which is why 1↔2/3↔4 looked correct). Re-selecting the
effect fired obj-18 with gates by then correct, which is why that "fixed" it.
Fix: `obj-pv33-busdefer` (deferlow) inserted between obj-12 and obj-pv2-busadd — the
entire pv2 bus-switch refresh now runs after obj-12's whole synchronous cascade
(item rebuild, gate flips, channel), independent of box positions. Recall's display
refresh enters at obj-pv2-busN below the deferlow and already ran in a deferred
context with gates matching the current bus — unaffected.
RETEST: cross-group switches (1/2→3, 1/2→INPUT, 3/4→1, INPUT→4 …) must now show
correct labels immediately; also re-check same-group switches and plain dial edits
for regressions (the refresh now lands one queue tick later).

## 32: pattrstorage preset system (replaces psys-* coll-based system)
Full cutover from the Control-31 `obj-psys-*` (coll-based, 49 objects) preset system to
one built on `pattrstorage`/`pattrforward`, following the mechanism validated in
`SP404_preset_TEST_v16.maxpat`. Generated by `sp404gen/build_control32.py` (run it to
regenerate from Control-31 after any further edits to that base file); structurally
validated by `sp404gen/validate_control32.py` (confirms no dangling references, no
orphaned inlets/outlets, all 40 pattr client varnames match the subscribe list — does
NOT confirm the patch runs correctly in Max, which requires actually opening it).
Diffed against Control-31: every non-psys object and connection is byte-for-byte
identical; only `psys-*` was removed and the new `obj-pv2-*` system added on top.

**Design, and where it necessarily diverges from the v16 prototype** (v16 was a
simplified mechanism test — no MIDI, no enum display, no dynamic per-bus menus):
- 40 pattr client objects (8 params × 5 buses), not v16's 35 — the prototype never
  covered the effect-select menu's real per-bus rebuild or the bus on/off toggle (CC19).
- Bus switch retargets `pattrforward` (send Bus%d_X) off the real bus-select `obj-12`,
  additive to its existing (untouched) `obj-19`/`obj-506`-series item-rebuild wiring.
- Display refresh for the 6 CC dials + toggle feeds a REAL value into their hot inlet
  (audible, matches deleted `psys-unres` behavior) — necessary so the downstream
  enum/SYNC pipeline (`expr $i2*1000+$i1` → gate → coll) recomputes. The effect-select
  menu (`obj-18`, plain `umenu`) instead gets a silent `set $1` PLUS an explicit
  broadcast into the 5 per-bus EFX gates' inlet 1 (`obj-pv2-efx-mfan`, replicates the
  deleted `psys-mfan`) — required because `set` doesn't fire `umenu`'s outlet, and the
  enum-mode derivation only re-runs when that outlet fires.
- Recall ordering (effect-select must land before CC values) is done via explicit
  `t`-object trigger sequencing, NOT a pattrstorage "priority" attribute — that
  attribute's existence/behavior on `live.*` parameter objects couldn't be verified
  without Max, so this uses the same technique the original system already proved.
- Hardware dispatch on recall (push all 5 buses' stored state to the real unit over
  MIDI, bypassing the UI) has no v16 analogue. It uses a SEPARATE set of 40 "hw-holder"
  ints (`obj-pv2-hwh-*`, distinct from the 40 display-shadow ints `obj-pv2-sh-*`) so
  dispatching a non-viewed bus can never leak into the currently-displayed control.
  Sequencing: `recall N` → deferlow → hw-dispatch (`uzi 5`, 1-indexed, confirmed against
  the deleted `psys-uzhw`'s own wiring) completes fully for all 5 buses FIRST, THEN the
  current bus's display refresh fires LAST, so it's the authoritative final state.
- SAVE/RECALL UI and PC 0-7→preset 1-8 mirror the deleted psys objects' UI/behavior,
  but pattrstorage's native `store N`/`recall N` eliminated all the old key-arithmetic
  objects (`psys-p1/p10/keyadd-*`) — slot number is used directly, no `(preset+1)*10+bus`
  key math needed.

### Bug found in first no-hardware Max test, fixed same session
User-reported symptoms (no hardware attached, watched MIDI out directly):
1. Every control (EFX menu, knobs, on/off button) sent its CC out TWICE.
2. RECALL worked, but visibly corrupted the CURRENTLY VIEWED bus's dials, even
   though the stored data for non-viewed buses (checked directly on the hidden bg
   objects) was correct.

Root cause (one bug, two symptoms): the "continuous tap" wire from each bg client
object into its shadow int (`obj-pv2-sh-*`, display) and holder int (`obj-pv2-hwh-*`,
hw-dispatch) was wired into the int object's HOT inlet 0. A Max `int` object's hot
inlet stores AND immediately re-outputs on any incoming value. Since:
  - `obj-pv2-sh-*`'s output feeds directly into the visible control's hot inlet, and
  - `obj-pv2-hwh-*`'s output feeds directly into a `ctlout`,
...every live edit (forwarded via pattrforward into the currently-targeted bg object,
which then fires because it changed) immediately echoed straight back out through
BOTH paths -- a second MIDI send on every edit (symptom 1), plus a spurious send on
whatever stale channel `obj-15` last held. During RECALL, `pattrstorage` updates all
40 bg objects in its own internal order (not bus-grouped, not otherwise controlled by
this patch), so ALL of them briefly flooded the single set of visible controls before
the deliberate post-recall refresh (which fires last, on purpose) could overwrite it
back to the correct current-bus value -- except the same hot-inlet tap kept re-firing
into the visible controls throughout that flood, racing the deliberate refresh
(symptom 2).

Fix: route the continuous tap into the int object's COLD inlet 1 instead (stores the
value silently, no output) for both `obj-pv2-sh-*` and `obj-pv2-hwh-*`. The deliberate
triggers (`sel_{param}` bang for display refresh, `hw-bussel` bang for hw-dispatch)
still target the HOT inlet 0, so they're the ONLY thing that makes these objects
output. Applied in `build_control32.py`; Control-32 regenerated and re-validated
(structural check + full non-psys diff against Control-31, still byte-identical).

**Re-tested by user in Max after the fix (2026-07-08, no hardware): confirmed working.**
Single CC-out per control action, and SAVE/RECALL now correctly refresh the
currently-viewed bus's dials without corruption.

### Persistence bug found on close/reopen, fixed same session
User closed Control-32.maxpat, got prompted to save a "presets" file, saved it,
reopened the patch — nothing could be recalled anymore.

Root cause: `pattrstorage` does NOT embed its data inside the .maxpat the way
`coll @embed 1` does (confirmed against Max's own docs, not assumed) — it always
persists to a separate companion JSON/XML file. `@savemode 1` (what was used) only
means "prompt to save that companion file when the patcher closes" — it has nothing
to do with embedding. Worse, `@autorestore 0` (copied verbatim from the v16
prototype's settings, which only cared about not sending MIDI on load) is the
attribute that makes pattrstorage automatically find and reload that companion file
on patch open — with it off, the freshly-saved file was never read back in, so
`pattrstorage` started every session completely empty regardless of what got saved.

User was asked and chose: keep pattrstorage's native companion-file model (not worth
re-engineering back to a single embedded file) but make it deterministic instead of
relying on the close-time prompt and default file-name guessing.

Fix: pinned explicit `read`/`write` messages to a fixed filename,
`Control32_presets.json` (bare filename — Max's docs confirm the patcher's own
folder is searched by default, so this travels correctly as long as the two files
stay together). `@savemode 0 @autorestore 1` — no more close-time prompt;
`write "Control32_presets.json"` fires automatically right after every SAVE-button
press (deferred one tick so the store completes first), so presets hit disk
immediately rather than depending on the user remembering to save/close, or a
dialog they might dismiss. `read "Control32_presets.json"` fires on load, after
`subscribe` completes. New objects: `obj-pv2-load-defer2`/`obj-pv2-read-msg` (load
side), `obj-pv2-save-defer`/`obj-pv2-write-msg` (save side).

**Note:** the presets file the user saved via the earlier (broken) close-prompt
went wherever that dialog defaulted to, NOT `Control32_presets.json` — it's an
orphan and can be ignored/deleted. The new mechanism will create
`Control32_presets.json` fresh, in the same folder as the .maxpat, the first time
SAVE is pressed after reopening with this fix.

User confirmed `Control32_presets.json` does get created in the right folder, but
after closing/reopening Max, RECALL for the saved preset still did nothing.

### Slot-numbering bug found on file-persistence retest, fixed same session
Root cause: `obj-pv2-slotmenu` is a plain `umenu` ("Preset 1".."Preset 8" items) --
umenus are 0-INDEXED, so selecting "Preset 1" outputs `0`, not `1`. That raw value
was fed straight into `prepend store`/`prepend recall` with no adjustment, so
pressing SAVE on "Preset 1" actually sent `store 0` to pattrstorage, not `store 1`.
Slot 0 is apparently enough of an edge case that it round-trips oddly through
pattrstorage's file format (worked live in-session, silently failed after a real
file save/reload) -- consistent with the exact symptom reported. The ORIGINAL
psys-* system had already solved this exact conversion (`psys-curpre -> +1`
before its own key math); this session's port dropped the key-math objects
correctly (pattrstorage doesn't need them) but incorrectly dropped the `+1` along
with them.

Fix: inserted `+1` (`obj-pv2-slot1-store`, `obj-pv2-slot1-rcl`) between
`slotmenu`'s raw output and the `store`/`recall` messages, so "Preset 1" now
correctly maps to pattrstorage slot 1. Also fixed a related bug this surfaced in
the PC-recall chain (`obj-pv2-pgt` section): it applied `+1` BEFORE splitting into
the display-set and recall-message branches, so both got the already-1-based
value -- meaning the on-screen slot display was off by one (PC=0 showed "Preset 2"
instead of "Preset 1") while recall itself happened to target the right slot only
by coincidence of both being consistently wrong. Restructured so the raw 0-based
PC value feeds the (0-indexed) display `set`, and `+1` is applied only on the
branch heading to `recall`.

**Re-tested by user in Max (2026-07-08, no hardware): confirmed working.**
SAVE -> close/reopen Max -> RECALL now round-trips correctly through
`Control32_presets.json`. PC 0-7 display-offset fix not separately re-tested yet
(low risk, same code path pattern as the verified button path).

## ARCHITECTURE (post-Control-16, updated Control-30)
- enum_k0..k5 colls: keyed etid*1000+CC -> final display text (128 entries per etid)
- Signal: live.dial -> expr $i2*1000+$i1 (i1=raw CC hot, i2=mode/etid cold from
  existing mode-cold-store int) -> gate (mode>=0) -> enum coll -> display msgbox
- Balance: dial -> coll cc2bal_kN (key=CC) -> gate (mode==-2) -> display msgbox
- Numeric (-1): unchanged original scale->sprintf path
- prm_k*[idx] = [lo, hi, mode]; mode: -1 numeric, -2 balance, >=0 etid
- EFX menu obj-18 items are DYNAMICALLY rebuilt per bus (obj-20/22/24/26/28
  clear/append msgs). Saved file only shows last state — don't trust static items.
- busid_BUS12/BUS34/INPUT colls: menu position -> effect index. DFX slots use keys 100-104.

### SYNC-dependent mode switching (added Control-30)
- Current effect index stored in obj-sync-ceidx (int), tapped from c3124 outlet 0.
- k5 dial (CC82, obj-498) tapped via obj-sync-sy01 (t i i):
    outlet 1 (fires FIRST): raw CC → per-handler CC stores (obj-sync-sl-cc etc.)
    outlet 0 (fires SECOND): int→bang via obj-sync-sy03 → bangs obj-sync-ceidx → effect idx
      → obj-sync-sy04 (route 34 36 39 45) → per-effect t b b handlers
- Per-effect handler (t b b):
    outlet 1 (bang, FIRST): bangs per-handler CC store → >= 1 → expr → writes mode to
      target knob's cold-store int (c3041/c3092/c3024 for k1/k4/k0)
    outlet 0 (bang, SECOND): bangs target knob's CC-value int (c3039/c3090/c3022)
      → t i b chain → cold-store outputs new mode → expr cold inlet updated;
      display refreshes on next knob movement.

## PRESET SYSTEM — VERIFIED ARCHITECTURE (test patch v16, July 2026)

### Core design (pattrforward + pattrstorage, user's methodology)
- 35 real parameter-enabled bg objects: live.dial (varname "BusN_ccXX") + live.menu
  (varname "BusN_efx") for each of 5 buses. These are pattrstorage's tracked clients.
- 7 visible controls (6 number boxes + 1 live.menu): NO varname, NOT pattr-tracked.
- autopattr object present (bare, unconnected) — REQUIRED for @subscribemode 1 to work.
- pattrstorage @subscribemode 1 + explicit 'subscribe <name1>..<name35>' sent via
  loadbang -> deferlow -> subscribe_msg -> pstore (registration before any bindto).
- After subscribe, a second deferlow fires busmenu '0' to trigger initial bus1 binding.

### Bus switch mechanism
- busmenu int outlet -> +1 -> bus_t (t b i):
  - out1 (int, FIRST): -> 7x sprintf 'send Bus%d_X' -> pattrforward retargets (write)
                        -> busN int (HOT inlet, stores AND outputs) -> 7x select 1-5
                        -> bang matching shadow int -> shadow outputs -> prepend set
                        -> visible control (silent display update)
  - out0 (bang, SECOND): unconnected (display handled by busN fan above)
- 35 shadow ints (one per bg object): tap bg object outputs, hold last value.
  select 1-5 bangs the correct one on bus switch.

### Write direction (user moves visible control)
- visible -> pattrforward (target = current bg varname via 'send BusN_X' message)
- pattrforward forwards value directly to bg live.dial/live.menu inlet
- pattrstorage tracks bg objects automatically (parameter_enable=1, proper attributes)

### Preset SAVE/RECALL
- Slot umenu (1-8) -> prepend store -> message right inlet (cold set);
  SAVE btn -> t b b: out1(first) bangs slotmenu -> fires prepend -> sets msg;
  out0(second) bangs store_msg -> 'store N' -> pattrstorage. (prepend store idiom)
- Same pattern for recall with prepend recall.
- After recall: pstore out0 -> deferlow -> t b -> bang busN -> busN outputs current
  bus -> 7 select -> shadows -> visible (display refresh after pattrstorage restores)

### CRITICAL LESSONS (hard-won)
1. pattrforward retargets via 'send <name>' message (NOT bare symbol). Use
   'sprintf send Bus%d_X' not 'sprintf symout Bus%d_X'.
2. pattr 'bindto' masks the target from pattrstorage — never use bindto on objects
   that pattrstorage must track.
3. autopattr (bare, no connections) MUST be present for @subscribemode 1 to work.
4. pattrstorage 'Client Objects' window shows LIVE values, not saved slots.
   Use 'storagewindow' message to pattrstorage to see per-slot saved data.
5. Visible controls must have NO varname — if they have a varname, pattrforward
   loops back to them instead of targeting the bg object.
6. 'set $1' on an int stores silently (no output). Feed bus number to int HOT
   inlet (inlet 0 with plain int) so it stores AND outputs immediately.
7. Subscribe list names must match bg object varnames EXACTLY (case-sensitive).
8. Use shadow ints (one per bg object) to hold last values — bg live.dial only
   outputs on change, not on bang. Shadow ints can be banged to re-output.
9. SAVE/RECALL button: use t b b — first bang fires slotmenu (sets prepend cold),
   second bang fires the store/recall message. Without first bang, saves to slot 0.
10. After pattrstorage recall, use deferlow before triggering display refresh —
    gives pattrstorage time to restore all 35 values before display reads them.
