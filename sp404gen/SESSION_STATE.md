## 34: MIDI Control Input + 128 presets with renaming
Generated by `sp404gen/build_control34.py` (from Control-33); structurally validated by
`sp404gen/validate_control34.py`. Full diff against Control-33 confirmed: 62 boxes added
(obj-c34-* namespace), 0 removed, 81 lines added, 0 removed, and exactly 4 field changes
on existing boxes (presets filename x2, `obj-pv2-pgsplit` range, `obj-pv2-slotmenu` items).

**(a) MIDI Control Input.** Lets an external MIDI controller drive the 6 dials, the EFX
select umenu, and the EFX on/off toggle — deliberately NOTHING else (not bus select, not
DFX slots, not presets), per the user's explicit scope. New "MIDI Control Input Device"
umenu (`obj-c34-indev`, item list cloned from the existing "MIDI Output Device" umenu
`obj-4` — same caveat as that one: it's a snapshot of the user's own MIDI ports captured
at some point, likely needs re-picking on whatever machine actually runs this) → `prepend
port` → one bare `ctlin` (all channels/controllers on the selected port; channel is
deliberately NOT filtered — the user didn't ask for it and SP-404 channel dispatch is an
output-side concept, unrelated to accepting external control input).
For each of the 8 targets: a `number` box ("MIDI CC selector") defaulting to the CC the
patch already sends to hardware for that control (16/17/18/80/81/82 for ctrl1-6, 83 for
EFX select, 19 for EFX on/off — confirmed against the actual `ctlout` objects and the
existing "Ctrl 1-3 = CC#16-18..." comment, not assumed). Per target: `ctlin`'s
controller-number outlet → `==` (hot inlet 0) against the CC selector (cold inlet 1) →
drives a `gate 1`'s control inlet 0; `ctlin`'s value outlet → the gate's data inlet 1.
Ordering relies on `ctlin` firing right-to-left (channel, then controller#, then value —
same guarantee already used everywhere else in this patch): controller# always reaches
`==`/gate-control before value reaches gate-data, so the gate's open/closed state is
always current before data arrives. When CC# matches, the raw value passes straight into
the target's own hot inlet 0 — the SAME inlet the user's mouse edits use — so external
control audibly sends CC out and updates pattrforward/pattrstorage exactly like a live
edit (this is deliberate: it's how "only these 8, and only via their real outputs" is
satisfied with no separate code path). EFX on/off gets an extra `>= 64` threshold
(`obj-c34-onoff-thresh`) converting ctlin's 0-127 value to live.toggle's 0/1.
⚠ UNVERIFIED: the assumption that live.dial/live.menu's own numeric range (already 0-127,
confirmed since their own outlets feed `ctlout` directly with no scale object) means a raw
incoming CC value can be fed straight into their hot inlet with no conversion. This is a
direct extension of already-verified patch behavior (same idiom used for DFX preset
restore in Control-33) but has never been tried with genuinely-external, unpredictable
input before.

**(b) 128 presets + renaming.** `obj-pv2-pgsplit` widened `split 0 7` → `split 0 127`
(PC 0-127 now all recall a preset; was PC 0-7 only). `obj-pv2-slotmenu` grows from 8
static items to 128 ("Preset 1".."Preset 128" defaults). Preset NAMES are intentionally
NOT part of the pattrstorage-based `Control34_presets.json` (that file is parameter data,
saved/loaded independently) — they live in a separate embedded `coll`
(`obj-c34-namecoll`, `@embed 1`, same embedding mechanism already proven via the existing
`lbl_k0`-style colls), keyed 1-128, storing ONLY the free-text part of each name
(default "Preset N"). The PC-number prefix is NEVER stored — it's recomputed as
(slot - 1) every time the menu is rebuilt from the coll, so a rename can never desync the
prefix from the actual slot/PC number.
Rebuild routine (`obj-c34-rebuild-t`/`-uzi`/`-split`/`-minus1`/`-sprintf`/
`-prependset`): "clear" the umenu, then `uzi 128 3` walks keys 1-128, building each
item as "append PC<n> - <name...>" and appending it. Uses a single-specifier
`sprintf PC%ld -` (same proven pattern as the existing `sprintf send Bus%d_X` objects —
deliberately AVOIDING an untested `sprintf ... %ld ... %s` combination) whose output
("PC<n> -") is fed into a bare `prepend`'s COLD (right) inlet, dynamically re-arming what
it prepends; the coll's looked-up name then hits `prepend`'s HOT (left) inlet, producing
"append PC<n> - <name...>" as one message straight into the umenu. Runs once on load
(`obj-c34-lb2`) and once after every rename.
Rename UI: `obj-c34-nameedit` (a `textedit` — genuinely novel, zero precedent elsewhere
in this codebase) outputs free text (no PC number typed by the user) → `obj-c34-namet`
(`t b b l`, right-to-left): text is stored into `obj-c34-namepack`'s cold inlet FIRST,
then the current slot (from `obj-c34-slotshadow`, the same cold-tapped "shadow int" idiom
used throughout this patch, +1) triggers `namepack`'s hot inlet to write [slot, name]
into `namecoll`, and only THEN (last) is the full rebuild kicked off — guaranteeing the
rebuild's coll lookups always see the just-written name. After the rebuild's "clear" wipes
the visible selection, `obj-c34-slotshadow` is banged again (from `uzi`'s done-outlet 1)
and `prepend set`s it back onto the umenu, restoring the highlighted item's (freshly
rebuilt) text.
⚠ UNVERIFIED, in order of risk: (1) `textedit`'s actual output behavior/timing (does it
fire on Enter? Tab? focus-loss only? all three?) — completely untested in this codebase;
(2) `prepend`'s right-inlet dynamically changing its stored prefix at runtime — standard
documented Max behavior but never exercised here before; (3) `uzi 128 3`'s outlet 1 being
the "done" bang (inferred from Max's standard 2-outlet uzi semantics, extrapolated to the
3-outlet form — this codebase's existing `uzi 5 3` usage never wired outlets 0/1 at all,
so there's no in-file precedent to confirm against).

Presets companion file renamed to `Control34_presets.json` (read/write msgs) — format
unchanged, still has no name/DFX data (names live in the embedded coll, not this file).

### Rebuild bug found in first Control-34 Max test, fixed same session
User-reported symptoms: MIDI Control Input worked correctly first try (item (b) above,
confirmed). The 128-preset system was completely broken: the slotmenu umenu was
unresponsive with nothing selectable, and SAVE/RECALL did nothing (so renaming, item (d),
couldn't even be attempted).

Root cause (one bug, both symptoms): `obj-c34-rebuild-sprintf` was built as
`sprintf PC%ld -` — missing the literal `append` selector word. Every one of the 128
rebuild messages sent to slotmenu therefore looked like `"PC5 - Preset 5"` instead of
`"append PC5 - Preset 5"`. A umenu doesn't recognize `PC5` as a message selector (it's
neither a known command like `append`/`clear`/`set` nor a bare int), so Max silently (or
with a console error) dropped every single append — after the load-time `clear`, the
menu was left with exactly 0 items. That explains BOTH symptoms directly: an empty umenu
has nothing to show when clicked ("unresponsive, nothing selectable"), and SAVE/RECALL
(which work by banging slotmenu to re-assert its current selection before building the
`store N`/`recall N` message) get no output from an item-less umenu, so the store/recall
messages never receive a valid slot argument.
Fix: `sprintf append PC%ld -` (the `append` word lives in the format string itself, since
the downstream `prepend` object only ever prepends whatever text it was last given — it
was never going to add "append" on its own).

While fixing this, also caught a second, latent bug in the same area (not yet visible to
the user, since it requires either a first-ever load or a rename to trigger, but would
have corrupted preset names silently): `obj-c34-slotshadow`'s single outlet fed BOTH the
rename-store chain (`slot1-name` → `namepack` → `namecoll`) AND the post-rebuild
selection-restore chain (`restore-pset`). Since the rebuild's "restore selection" step
bangs this shadow on EVERY rebuild (at load, and after every rename), it was also firing
the rename-store chain every time — writing whatever stale (or, on first load,
uninitialized) value happened to be sitting in `namepack`'s cold inlet into `namecoll` at
the current slot, silently overwriting that preset's name. Fix: split into two separate
shadow ints, `obj-c34-slotshadow` (rename-fetch only) and `obj-c34-slotshadow-restore`
(selection-restore only), both cold-tapped from the same slotmenu output but with no
shared consumer — mirrors the "hw-holder vs display-shadow" split already used elsewhere
in this patch specifically to prevent this class of cross-talk.

Both fixes are in `build_control34.py`; Control-34 regenerated (779 objects, 1241 lines)
and re-validated (`validate_control34.py` now also asserts the sprintf text contains
"append" and that the two shadows have no cross-wiring).
RETEST: umenu must show all 128 items ("PC0 - Preset 1".."PC127 - Preset 128") on load
and be selectable; SAVE/RECALL must work; then retest renaming (MAX-TEST item d above),
which couldn't be attempted at all before this fix.

### Second rebuild bug found on retest, fixed same session — prepend abandoned
User retested after the fix above: still broken, but now specifically "just the preset
menu" (confirmed everything else -- dials, bus select, MIDI Control Input -- unaffected),
with the Max console flooded with `umenu: doesn't understand "Preset"` on load.

That error is the smoking gun: the message actually reaching slotmenu started with the
bare word `Preset`, not `PC5` (the previous bug) and not even `append PC5 -`. This means
`obj-c34-rebuild-prependset` (a bare `prepend`, no fixed argument, whose right/cold inlet
was fed `"append PC<n> -"` at runtime to dynamically set its prefix) never actually
adopted that prefix — it silently stayed empty and just passed the coll's raw stored
value (`Preset5`, one atom) straight through untouched. The "dynamically re-armed
prepend" technique documented as unverified in the original "34" section write-up (⚠
UNVERIFIED item 2) was in fact the bug: `prepend`'s right inlet does not take an
arbitrary multi-atom message and adopt it as a new multi-word prefix the way a
fixed creation argument does.

Fix: abandoned `prepend` for this entirely. Replaced the two-object
sprintf-then-prepend chain with a SINGLE dual-specifier sprintf,
`sprintf append PC%ld - %s` — the `%ld` (PC number) and `%s` (coll-stored name) are
combined in one object, with no intermediate hand-off between objects to get wrong.
%ld is the first specifier (hot/leftmost inlet 0, fires last and triggers the output);
%s is the second (cold/rightmost inlet 1, fires first). `obj-c34-rebuild-split` (`t i i`)
still sequences this: outlet 1 (FIRST) → namecoll lookup → sprintf's cold inlet 1;
outlet 0 (SECOND) → `- 1` → sprintf's hot inlet 0, producing
`"append PC<n> - <name>"` straight into slotmenu, no `prepend` involved at all.
Also fixed while in there: `obj-c34-namecoll`'s default values are now exactly ONE atom
per entry (`Preset5`, not `['Preset', '5']`) — `%s` substitutes exactly one atom, so the
old 2-atom default would have silently dropped the number from every un-renamed preset's
displayed name (latent, would not have been caught by the console-error symptom above).
`obj-c34-rebuild-prependset` no longer exists. `validate_control34.py` updated to check
the exact sprintf text, that prependset is gone, and that every namecoll value is a
single atom.
RETEST: same as above (umenu must show all 128 items and be selectable; SAVE/RECALL must
work; renaming must work and show "PC<n> - <name>" immediately) — this is the third
attempt at the same test, unverified until confirmed in Max.

### Third and fourth bugs found on retest, fixed same session — root-caused via docs, not guessing
User retested: (1) all 128 items now show and are selectable, but numbering was shifted —
started at "PC2 - Preset 3", ended at "PC129 - Preset 128"; (2) SAVE/RECALL confirmed
working; (3) renaming still did nothing at all.

This time, instead of guessing again, looked up Max's own `uzi` and `textedit` reference
documentation (docs.cycling74.com, via web search) before touching code. Both remaining
bugs turned out to be misunderstandings of documented object behavior, not timing/ordering
issues like the first two:

**Bug 3 — `uzi`'s second argument is a counter BASE VALUE, not an outlet selector.**
`obj-c34-rebuild-uzi` was built as `uzi 128 3`, intended as "128 repetitions, counter on
the 3rd outlet". That's not what the argument means: uzi's outlets are always exactly
[bang-repeat, done-bang, counter] regardless of arguments (docs: "the uzi object has
three outlets"); the actual syntax is `uzi <repetitions> <base>`, where the OPTIONAL
second argument sets the STARTING VALUE the counter counts from (default 1). `uzi 128 3`
therefore counted 3,4,...,130 (128 values) instead of 1,2,...,128 — exactly matching the
reported shift: first entry from counter=3 (PC=2, namecoll(3)="Preset3"), last entry from
counter=130, whose PC number computes to 129 but whose namecoll lookup (key 130, past the
128 valid keys) fails and silently leaves the cold %s inlet holding the last successful
lookup's value ("Preset128" from counter=128) — reproducing "PC129 - Preset128" exactly.
Fix: `uzi 128` (no second argument, defaults the base to 1).
Note: this is a mistake specific to writing NEW code with the wrong mental model of the
argument — not something inherited from Control-32/33's existing `obj-pv2-hw-uzi`, which
was re-checked and is simply `uzi 5` (correct, no base argument) despite an earlier,
mistaken debugging note in this session claiming otherwise (misread the debug print's own
`numoutlets` field as part of the object's text).

**Bug 4 — `textedit` defaults to `keymode 0`, where Return never outputs anything.**
`obj-c34-nameedit` was created with no attributes at all. Per Max's textedit reference,
`keymode 0` (the default) treats Return as a normal line break with NO output; only
`keymode 1` makes Return "output the entire contents of the current buffer". Without it,
the entire rename chain (`namet` → `namepack` → `namecoll` → rebuild) could never fire no
matter what the user typed — this fully explains "renaming doesn't work" as a totally
separate bug from bug 3 above (unrelated to the uzi/numbering issue).
Fix: added `keymode: 1` to `obj-c34-nameedit`'s box definition.

Both fixes are minimal, single-field changes (`build_control34.py` diff: `obj-c34-rebuild-
uzi` text `'uzi 128 3'` → `'uzi 128'`; `obj-c34-nameedit` gains `keymode: 1`; nothing else
changed). `validate_control34.py` now asserts both.
RETEST: (i) menu must read "PC0 - Preset 1" through "PC127 - Preset 128", in order, no
stale/duplicated trailing names; (ii) SAVE/RECALL (already confirmed, shouldn't have
changed); (iii) select a preset, type a name, press Enter/Return — the menu should
immediately show "PC<n> - <name>" with the same slot still selected. This is the fourth
attempt at this specific test.

### Fifth bug found on retest — the keymode/outputmode attributes never actually applied
User retested: (i) numbering fully correct now, "PC0 - Preset 1" through
"PC127 - Preset 128", no stale names — bug 3 confirmed fixed. (ii) SAVE/RECALL still
fine. (iii) Renaming still broken, but differently: pressing Return just inserts a line
break in the text box (not a commit) exactly like keymode 0's documented behavior; only
clicking OUTSIDE the text box (defocus) commits anything. And what gets committed is
wrong: the PC-number prefix is fine, but the name portion always shows the literal word
"text" instead of whatever was typed.

Both symptoms point to the same root cause: `keymode: 1` and (this session, in response)
`outputmode: 1`, set as top-level JSON keys on obj-c34-nameedit's box definition (the same
mechanism used successfully for every other UI attribute in this codebase, e.g. umenu's
`items`, live.dial's `parameter_enable`), did NOT take effect for `textedit` specifically.
The object kept its defaults: keymode 0 (Return does nothing but insert a line break --
matches "changes paragraph" exactly) and outputmode 0 (output is a `"text <words...>"`
MESSAGE, not a bare symbol -- confirmed against a Max forums thread specifically about
this exact "text" prefix gotcha). Since `obj-c34-namepack` (`pack 0 s`) only keeps the
FIRST atom sent to its symbol inlet, receiving `["text", "MyName"]` silently kept just
"text" and discarded the actual typed name -- reproducing "always text regardless of
what you typed" exactly. (PC-number prefix was unaffected since it's computed independently
by the rebuild's sprintf, not part of this chain.)

Fix: abandoned the creation-time attribute keys entirely. Max's own textedit reference
documents BOTH settings as also configurable via an explicit MESSAGE to the object's
inlet ("the message keymode 1 causes..."), which is a different, message-passing
mechanism from a saved creation attribute -- added `obj-c34-nameedit-lb` (a dedicated
loadbang) feeding two message boxes, `keymode 1` and `outputmode 1`, both wired into
`obj-c34-nameedit`'s inlet at load. `validate_control34.py` updated to check these
messages and their wiring instead of the (apparently inert) `keymode` JSON key.
RETEST: press Return in the rename box -- must commit (not insert a line break); the
resulting preset label must show the actual typed name, not the word "text". This is the
fifth attempt at the renaming half of this test; numbering and SAVE/RECALL are confirmed
already and don't need retesting.

### Sixth bug found on retest — outputmode never fixes it; textedit's "text" prefix is unconditional
User retested: Return now commits (bug 4's keymode fix confirmed working). But the
"text" problem persisted exactly as before -- typed name still replaced by the literal
word "text" -- meaning the `outputmode 1` message had no effect either.

Looked this up properly this time (a Max forums thread titled almost exactly "How to
delete 'text' that is prepended to output of textedit object?"): `textedit` ALWAYS
prepends the literal selector `text` to whatever it outputs, as an actual message
selector -- e.g. typing "MyKit" produces the message `text MyKit`, not the symbol
`MyKit`. This is NOT something `outputmode` turns off (that assumption, made when fixing
bug 4, was simply wrong -- `outputmode` governs a different aspect of formatting, not
whether the "text" selector is present). The confirmed, standard fix used throughout Max
patches for this exact behavior is a `route text` object, which matches the "text"
selector and forwards everything after it, stripped, through its first outlet.

This also surfaced a second, previously-latent defect: preset names can be MORE than one
word (multiple atoms, once "text" is stripped by route), but `obj-c34-namepack` (`pack 0
s`) only keeps the first atom sent to a symbol inlet, and the rebuild's `sprintf`'s `%s`
specifier also only substitutes exactly one atom -- both would have silently truncated
any multi-word rename to its first word even after the "text" bug was fixed. Fixed both
at once:
- `obj-c34-route-text` (`route text`) inserted between `obj-c34-nameedit` and
  `obj-c34-namet`, stripping the "text" selector before anything else sees the message.
- `obj-c34-namet` restructured `t b b l` → `t b l b`: out2 (FIRST) arms `obj-c34-namepack`
  cold inlet with the current slot number (a SINGLE atom -- this direction of dynamic
  `prepend` re-arming is fine, unlike bug 2's failed multi-atom attempt); out1 (SECOND)
  passes the actual typed words (list, any length) into `namepack`'s hot inlet, producing
  `[slot, word1, word2, ...]` into `namecoll`; out0 (LAST) kicks off the rebuild.
  `obj-c34-namepack` changed from `pack 0 s` to a bare `prepend`.
- Rebuild routine: `obj-c34-rebuild-sprintf` reverted to single-specifier
  `sprintf append PC%ld -` (just the PC number again); combining it with the coll's
  (possibly multi-atom) stored name is now `obj-c34-rebuild-zljoin` (`zl.join`), which
  concatenates two lists of any length -- left/hot inlet is the first segment and
  triggers output, right/cold inlet is the second segment. No `%s`, no re-armed
  `prepend`, no atom-count assumptions anywhere in this path anymore.
- Removed `obj-c34-nameedit-outmode` (the ineffective `outputmode 1` message) entirely.
`validate_control34.py` updated throughout for the new object names and wiring.
RETEST: rename a preset to something with a SPACE in it (e.g. "My Kit") -- the full
phrase must appear, not just the first word, not the word "text". This is the sixth
attempt at the renaming half of this test.

### Rebuilt from scratch on pattrstorage's own native slot-naming protocol
User retested: renamed labels showed as e.g. "PC0 - symbol Preset1" (the literal word
"symbol" appearing, not the typed text), and pressing Return in the textedit box did
nothing at all -- both regressions from the previous (confirmed-working) round, and both
inside the from-scratch coll/uzi/sprintf/zl.join system this session had been iterating
on for five rounds already.

The user also supplied a working reference patch of their own (`MIDI_CC_scene_morph.maxpat`,
uploaded, not committed to this repo) that renames a pattrstorage-backed menu. Tracing it
revealed something this session didn't know: **`pattrstorage` has a native slot-naming
protocol**, independent of the classic grid `preset` UI object --
- `getslotnamelist` sent to pattrstorage makes it emit, via its own outlet, one
  `slotname <preset#> <name>` message per slot, followed by a bare `slotname done`.
- `slotname <preset#> <name>` sent TO pattrstorage renames that slot.
This is a real, native pattrstorage feature (confirmed by the reference patch sending it
directly to a bare `pattrstorage <name> @savemode 2` object, the same kind of object this
patch already uses as `obj-pv2-pattrstorage` for its main preset values) -- not something
that needs a custom coll, a rebuild loop, or careful multi-object hand-offs to reinvent.
The entire from-scratch rename/rebuild system (namecoll, uzi, sprintf, zl.join, prepend,
the shadow-int cross-talk fixes) is now DELETED and replaced with wiring adapted directly
from the reference patch's `obj-22`/`obj-13`/`obj-30` (rename-send) and `menu-helper`
(clear/gate/rebuild) subpatchers:

- Rename-send: `obj-c34-slot1` (`+ 1`) continuously tracks the current 1-based slot
  (no bang-fetch needed -- fed directly and hot from `obj-pv2-slotmenu`'s own outlet, so
  by the time the user finishes typing it's already current) -> `obj-c34-namepack`
  (`pack s i`, hot=text/cold=slot#) -> `obj-c34-namemsg` (message `slotname $2 $1`,
  reordering pack's `[text, slot]` into pattrstorage's own `slotname <slot> <text>`
  syntax) -> `obj-c34-name-t` (`t b l`, right-to-left): out1 (FIRST) sends the rename
  straight into `obj-pv2-pattrstorage`; out0 (SECOND) triggers a refresh once the rename
  has actually landed.
- Refresh (shared by loadbang and post-rename): `obj-c34-refresh-t` (`t b b`): out1
  (FIRST) -> `obj-c34-clearopen` (`t 1 clear`) clears the menu and opens
  `obj-c34-gate`; out0 (SECOND) sends `getslotnamelist` to pattrstorage.
- Parsing pattrstorage's reply (a NEW tap on `obj-pv2-pattrstorage`'s existing outlet,
  purely additive -- nothing existing was touched): `obj-c34-slotname-route`
  (`route slotname`) -> `obj-c34-slotname-done` (`route done`): matched "done" closes
  the gate (`obj-c34-gateclose`, `t 0`) AND restores the visible selection
  (`obj-c34-slotshadow`, banged, -> `prepend set` -> slotmenu); unmatched `<n> <name>`
  goes to `obj-c34-slotname-unpack` (`unpack 0 s`), whose two ALREADY-SEPARATE outputs
  (int n, symbol name -- no coll, no %s, no re-armed prepend needed) feed
  `obj-c34-slotname-minus1`/`obj-c34-slotname-sprintf` (`sprintf append PC%ld -`) and
  `obj-c34-slotname-zljoin` (`zl.join`, concatenating the PC-prefix with the name)
  respectively, landing on `obj-c34-gate`'s data inlet -> `obj-pv2-slotmenu`.

## 32: pattrstorage preset system (replaces psys-* coll-based system)
Full cutover from the Control-31 `obj-psys-*` (coll-based, 49 objects) preset system to
one built on `pattrstorage`/`pattrforward`, following the mechanism validated in
`SP404_preset_TEST_v16.maxpat`. Generated by `sp404gen/build_control32.py` (run it to
regenerate from Control-31 after any further edits to that base file); structurally
validated by `sp404gen/validate_control32.py` (confirms no dangling references, no
orphaned inlets/outlets, all 40 pattr client varnames match the subscribe list — does
NOT confirm the patch runs correctly in Max, which requires actually opening it).
Diffed against Control-31: every non-psys object and connection is byte-for-byte
identical; only `psys-*` was removed and the new `obj-pv2-*` system added on top.

**Design, and where it necessarily diverges from the v16 prototype** (v16 was a
simplified mechanism test — no MIDI, no enum display, no dynamic per-bus menus):
- 40 pattr client objects (8 params × 5 buses), not v16's 35 — the prototype never
  covered the effect-select menu's real per-bus rebuild or the bus on/off toggle (CC19).
- Bus switch retargets `pattrforward` (send Bus%d_X) off the real bus-select `obj-12`,
  additive to its existing (untouched) `obj-19`/`obj-506`-series item-rebuild wiring.
- Display refresh for the 6 CC dials + toggle feeds a REAL value into their hot inlet
  (audible, matches deleted `psys-unres` behavior) — necessary so the downstream
  enum/SYNC pipeline (`expr $i2*1000+$i1` → gate → coll) recomputes. The effect-select
  menu (`obj-18`, plain `umenu`) instead gets a silent `set $1` PLUS an explicit
  broadcast into the 5 per-bus EFX gates' inlet 1 (`obj-pv2-efx-mfan`, replicates the
  deleted `psys-mfan`) — required because `set` doesn't fire `umenu`'s outlet, and the
  enum-mode derivation only re-runs when that outlet fires.
- Recall ordering (effect-select must land before CC values) is done via explicit
  `t`-object trigger sequencing, NOT a pattrstorage "priority" attribute — that
  attribute's existence/behavior on `live.*` parameter objects couldn't be verified
  without Max, so this uses the same technique the original system already proved.
- Hardware dispatch on recall (push all 5 buses' stored state to the real unit over
  MIDI, bypassing the UI) has no v16 analogue. It uses a SEPARATE set of 40 "hw-holder"
  ints (`obj-pv2-hwh-*`, distinct from the 40 display-shadow ints `obj-pv2-sh-*`) so
  dispatching a non-viewed bus can never leak into the currently-displayed control.
  Sequencing: `recall N` → deferlow → hw-dispatch (`uzi 5`, 1-indexed, confirmed against
  the deleted `psys-uzhw`'s own wiring) completes fully for all 5 buses FIRST, THEN the
  current bus's display refresh fires LAST, so it's the authoritative final state.
- SAVE/RECALL UI and PC 0-7→preset 1-8 mirror the deleted psys objects' UI/behavior,
  but pattrstorage's native `store N`/`recall N` eliminated all the old key-arithmetic
  objects (`psys-p1/p10/keyadd-*`) — slot number is used directly, no `(preset+1)*10+bus`
  key math needed.

### Bug found in first no-hardware Max test, fixed same session
User-reported symptoms (no hardware attached, watched MIDI out directly):
1. Every control (EFX menu, knobs, on/off button) sent its CC out TWICE.
2. RECALL worked, but visibly corrupted the CURRENTLY VIEWED bus's dials, even
   though the stored data for non-viewed buses (checked directly on the hidden bg
   objects) was correct.

Root cause (one bug, two symptoms): the "continuous tap" wire from each bg client
object into its shadow int (`obj-pv2-sh-*`, display) and holder int (`obj-pv2-hwh-*`,
hw-dispatch) was wired into the int object's HOT inlet 0. A Max `int` object's hot
inlet stores AND immediately re-outputs on any incoming value. Since:
  - `obj-pv2-sh-*`'s output feeds directly into the visible control's hot inlet, and
  - `obj-pv2-hwh-*`'s output feeds directly into a `ctlout`,
...every live edit (forwarded via pattrforward into the currently-targeted bg object,
which then fires because it changed) immediately echoed straight back out through
BOTH paths -- a second MIDI send on every edit (symptom 1), plus a spurious send on
whatever stale channel `obj-15` last held. During RECALL, `pattrstorage` updates all
40 bg objects in its own internal order (not bus-grouped, not otherwise controlled by
this patch), so ALL of them briefly flooded the single set of visible controls before
the deliberate post-recall refresh (which fires last, on purpose) could overwrite it
back to the correct current-bus value -- except the same hot-inlet tap kept re-firing
into the visible controls throughout that flood, racing the deliberate refresh
(symptom 2).

Fix: route the continuous tap into the int object's COLD inlet 1 instead (stores the
value silently, no output) for both `obj-pv2-sh-*` and `obj-pv2-hwh-*`. The deliberate
triggers (`sel_{param}` bang for display refresh, `hw-bussel` bang for hw-dispatch)
still target the HOT inlet 0, so they're the ONLY thing that makes these objects
output. Applied in `build_control32.py`; Control-32 regenerated and re-validated
(structural check + full non-psys diff against Control-31, still byte-identical).

**Re-tested by user in Max after the fix (2026-07-08, no hardware): confirmed working.**
Single CC-out per control action, and SAVE/RECALL now correctly refresh the
currently-viewed bus's dials without corruption.

### Persistence bug found on close/reopen, fixed same session
User closed Control-32.maxpat, got prompted to save a "presets" file, saved it,
reopened the patch — nothing could be recalled anymore.

Root cause: `pattrstorage` does NOT embed its data inside the .maxpat the way
`coll @embed 1` does (confirmed against Max's own docs, not assumed) — it always
persists to a separate companion JSON/XML file. `@savemode 1` (what was used) only
means "prompt to save that companion file when the patcher closes" — it has nothing
to do with embedding. Worse, `@autorestore 0` (copied verbatim from the v16
prototype's settings, which only cared about not sending MIDI on load) is the
attribute that makes pattrstorage automatically find and reload that companion file
on patch open — with it off, the freshly-saved file was never read back in, so
`pattrstorage` started every session completely empty regardless of what got saved.

User was asked and chose: keep pattrstorage's native companion-file model (not worth
re-engineering back to a single embedded file) but make it deterministic instead of
relying on the close-time prompt and default file-name guessing.

Fix: pinned explicit `read`/`write` messages to a fixed filename,
`Control32_presets.json` (bare filename — Max's docs confirm the patcher's own
folder is searched by default, so this travels correctly as long as the two files
stay together). `@savemode 0 @autorestore 1` — no more close-time prompt;
`write "Control32_presets.json"` fires automatically right after every SAVE-button
press (deferred one tick so the store completes first), so presets hit disk
immediately rather than depending on the user remembering to save/close, or a
dialog they might dismiss. `read "Control32_presets.json"` fires on load, after
`subscribe` completes. New objects: `obj-pv2-load-defer2`/`obj-pv2-read-msg` (load
side), `obj-pv2-save-defer`/`obj-pv2-write-msg` (save side).

**Note:** the presets file the user saved via the earlier (broken) close-prompt
went wherever that dialog defaulted to, NOT `Control32_presets.json` — it's an
orphan and can be ignored/deleted. The new mechanism will create
`Control32_presets.json` fresh, in the same folder as the .maxpat, the first time
SAVE is pressed after reopening with this fix.

User confirmed `Control32_presets.json` does get created in the right folder, but
after closing/reopening Max, RECALL for the saved preset still did nothing.

### Slot-numbering bug found on file-persistence retest, fixed same session
Root cause: `obj-pv2-slotmenu` is a plain `umenu` ("Preset 1".."Preset 8" items) --
umenus are 0-INDEXED, so selecting "Preset 1" outputs `0`, not `1`. That raw value
was fed straight into `prepend store`/`prepend recall` with no adjustment, so
pressing SAVE on "Preset 1" actually sent `store 0` to pattrstorage, not `store 1`.
Slot 0 is apparently enough of an edge case that it round-trips oddly through
pattrstorage's file format (worked live in-session, silently failed after a real
file save/reload) -- consistent with the exact symptom reported. The ORIGINAL
psys-* system had already solved this exact conversion (`psys-curpre -> +1`
before its own key math); this session's port dropped the key-math objects
correctly (pattrstorage doesn't need them) but incorrectly dropped the `+1` along
with them.

Fix: inserted `+1` (`obj-pv2-slot1-store`, `obj-pv2-slot1-rcl`) between
`slotmenu`'s raw output and the `store`/`recall` messages, so "Preset 1" now
correctly maps to pattrstorage slot 1. Also fixed a related bug this surfaced in
the PC-recall chain (`obj-pv2-pgt` section): it applied `+1` BEFORE splitting into
the display-set and recall-message branches, so both got the already-1-based
value -- meaning the on-screen slot display was off by one (PC=0 showed "Preset 2"
instead of "Preset 1") while recall itself happened to target the right slot only
by coincidence of both being consistently wrong. Restructured so the raw 0-based
PC value feeds the (0-indexed) display `set`, and `+1` is applied only on the
branch heading to `recall`.

**Re-tested by user in Max (2026-07-08, no hardware): confirmed working.**
SAVE -> close/reopen Max -> RECALL now round-trips correctly through
`Control32_presets.json`. PC 0-7 display-offset fix not separately re-tested yet

## PRESET SYSTEM (added Control-31, obj-psys-* namespace)
Deviation from S-1 template: uses embedded colls (not pattrstorage) — integrates with
the existing coll pipeline, keeps single-file distribution, presets saved with patch.

- ROW FORMAT (deliberately REVERSED): [v82 v81 v80 v18 v17 v16 onoff menupos]
  Reason: unpack fires outlets right-to-left, so menupos (effect select) fires FIRST —
  required both for MIDI order (CC83 before knob CCs) and so prm ranges/modes are set
  before dial values arrive. onoff stored raw 0/1 (× 127 only at ctlout dispatch).
- coll busstate (keys 1-5 = bus): live shadow of each bus's UI state. Written
  continuously: dials/toggle/menu → pak 8 → t b l → pack 0 l (key cold via
  prepend set, from bus idx + 1) → busstate. Key updated BEFORE restore on bus switch.
- coll presets @embed 1 (keys P*10+b, P=1-8, b=1-5): 40 rows, saved with the patch.
- BUS SWITCH RESTORE: obj-12 → psys-curbus int → psys-busres-t (t i i i, fires r→l):
  (2) +1 → pack key (via t i i → prepend set) AND → obj-15 channel
  (1) msg [1] → bsdemux control  (0) bus key → busstate query
  → gate 2 1 demux out0 → unpack → menupos: silent [set $1] to obj-18 + injection
  into all 5 EFX gates' inlet 1 (only active bus's gate is open) → full label/prm/
  SYNC machinery fires with NO MIDI; then onoff + 6 dials restored AUDIBLY (same CC
  values hardware already has = no state change, but displays refresh correctly).
- COLL OUTPUT DEMUX: busstate and presets each have a gate 2 1 on their outlet,
  control set by msg [1]/[2] immediately before each query (synchronous, race-free):
  busstate: 1=UI restore, 2=save copy. presets: 1=hw dispatch, 2=recall copy.
- SAVE: t b b → (r) bang curpre → +1 → *10 → cold key adders; (l) uzi 5 → per bus:
  set demux 2, query busstate[b], key=(P+1)*10+b → zl join → presets store.
- RECALL: t b b b b (r→l): (3) bang curpre/base; (2) uzi 5 hw dispatch — per bus:
  demux 1, channel b → obj-15, presets[key] → unpack → CC83 (obj-30), CC19 via
  * 127 (obj-456), CC16/17/18/80/81/82 (obj-459/467/475/483/491/499), all inlet 0
  (bypasses UI); (1) uzi 5 copy presets→busstate; (0) bang curbus → full UI +
  channel restore for the currently-viewed bus.
- MIDI CONTROL: bare pgmin (all ports/channels) → split 0 7 → t i i i:
  set preset umenu silently, update curpre, trigger RECALL. PC 0-7 = presets 1-8.
- loadbang init: pack key = set 1 (BUS 1), preset umenu = set 0. NO MIDI sent on load.

## PRESET SYSTEM — VERIFIED ARCHITECTURE (test patch v16, July 2026)

### Core design (pattrforward + pattrstorage, user's methodology)
- 35 real parameter-enabled bg objects: live.dial (varname "BusN_ccXX") + live.menu
  (varname "BusN_efx") for each of 5 buses. These are pattrstorage's tracked clients.
- 7 visible controls (6 number boxes + 1 live.menu): NO varname, NOT pattr-tracked.
- autopattr object present (bare, unconnected) — REQUIRED for @subscribemode 1 to work.
- pattrstorage @subscribemode 1 + explicit 'subscribe <name1>..<name35>' sent via
  loadbang -> deferlow -> subscribe_msg -> pstore (registration before any bindto).
- After subscribe, a second deferlow fires busmenu '0' to trigger initial bus1 binding.

### Bus switch mechanism
- busmenu int outlet -> +1 -> bus_t (t b i):
  - out1 (int, FIRST): -> 7x sprintf 'send Bus%d_X' -> pattrforward retargets (write)
                        -> busN int (HOT inlet, stores AND outputs) -> 7x select 1-5
                        -> bang matching shadow int -> shadow outputs -> prepend set
                        -> visible control (silent display update)
  - out0 (bang, SECOND): unconnected (display handled by busN fan above)
- 35 shadow ints (one per bg object): tap bg object outputs, hold last value.
  select 1-5 bangs the correct one on bus switch.

### Write direction (user moves visible control)
- visible -> pattrforward (target = current bg varname via 'send BusN_X' message)
- pattrforward forwards value directly to bg live.dial/live.menu inlet
- pattrstorage tracks bg objects automatically (parameter_enable=1, proper attributes)

### Preset SAVE/RECALL
- Slot umenu (1-8) -> prepend store -> message right inlet (cold set);
  SAVE btn -> t b b: out1(first) bangs slotmenu -> fires prepend -> sets msg;
  out0(second) bangs store_msg -> 'store N' -> pattrstorage. (prepend store idiom)
- Same pattern for recall with prepend recall.
- After recall: pstore out0 -> deferlow -> t b -> bang busN -> busN outputs current
  bus -> 7 select -> shadows -> visible (display refresh after pattrstorage restores)

### CRITICAL LESSONS (hard-won)
1. pattrforward retargets via 'send <name>' message (NOT bare symbol). Use
   'sprintf send Bus%d_X' not 'sprintf symout Bus%d_X'.
2. pattr 'bindto' masks the target from pattrstorage — never use bindto on objects
   that pattrstorage must track.
3. autopattr (bare, no connections) MUST be present for @subscribemode 1 to work.
4. pattrstorage 'Client Objects' window shows LIVE values, not saved slots.
   Use 'storagewindow' message to pattrstorage to see per-slot saved data.
5. Visible controls must have NO varname — if they have a varname, pattrforward
   loops back to them instead of targeting the bg object.
6. 'set $1' on an int stores silently (no output). Feed bus number to int HOT
   inlet (inlet 0 with plain int) so it stores AND outputs immediately.
7. Subscribe list names must match bg object varnames EXACTLY (case-sensitive).
8. Use shadow ints (one per bg object) to hold last values — bg live.dial only
   outputs on change, not on bang. Shadow ints can be banged to re-output.
9. SAVE/RECALL button: use t b b — first bang fires slotmenu (sets prepend cold),
   second bang fires the store/recall message. Without first bang, saves to slot 0.
10. After pattrstorage recall, use deferlow before triggering display refresh —
    gives pattrstorage time to restore all 35 values before display reads them.
